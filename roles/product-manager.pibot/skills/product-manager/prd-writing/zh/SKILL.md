# 需求文档

主题：{需求主题}
材料：{已有材料}

## 步骤
1. 读完已有材料；缺少关键信息时先问（目标用户、要解决的问题、成功标准），不要自己编。
2. 用一句话写出问题陈述：「<谁> 在 <什么场景> 下 <遇到什么困难>，导致 <什么后果>。」
3. 写用户故事，再给每个故事写验收标准（用「假如 / 当 / 那么」或可勾选的清单）。
4. 划范围：这次必须有（Must）/ 最好有（Should）/ 以后再说（Later）/ 不做（非目标）。
5. 列假设、风险、依赖、待决定的问题。
6. 文档保存在授权主工作位置，遵守本次实际写入权限。

## 模板

```
# <功能名> 需求文档
版本 / 日期 / 作者

## 1. 背景与问题
问题陈述：…
证据：用户原话、数据（注明来源）

## 2. 目标与成功标准
- 目标：…
- 衡量方式：指标 + 目标值 + 统计口径

## 3. 目标用户与场景

## 4. 需求
| 编号 | 用户故事 | 优先级 | 验收标准 |
|---|---|---|---|
| R1 | 作为 <角色>，我想要 <做什么>，以便 <得到什么> | Must | 1. 假如…当…那么… |

## 5. 非目标
## 6. 交互与设计要点（链接设计稿）
## 7. 假设、风险与依赖
## 8. 待决定的问题（谁来定、什么时候前）
```

## 验收标准自查
- 每条都能由测试或用户明确判断「是 / 否」。
- 不写「快」「好用」这类无法检验的词，换成具体数字或行为。
- 覆盖出错和边界情况，不只写正常路径。

## 使用边界

优先使用已有信息；用户的数量、格式和任务范围优先于本文默认模板。工具权限、主目录/附加只读、Plan 模式与预算以当次实际能力为准；不换工具规避拒绝。这里只给工作方法，不授权写入、命令、付费、发送、提交或发布；未执行/验证的步骤如实标明。
